## My engineering habits

```text
idea -> small scope -> readable implementation -> verification -> documented release
```

I prefer small, reviewable changes over large unexplained rewrites. A good project should make its purpose clear, provide a repeatable setup path, and include enough validation that another developer can trust the next change.

<details>
<summary><strong>Debugging field notes</strong></summary>

1. Reproduce the problem before changing the code.
2. Reduce the problem to the smallest useful example.
3. Check the data shape before blaming the interface.
4. Write down the fix so the same bug has less room to return.

The best debugging session is the one that leaves the codebase easier to reason about than before.

</details>
