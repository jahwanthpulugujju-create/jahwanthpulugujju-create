## Signal, not noise

> I build software that makes the next decision clearer: a dashboard that explains the data, a workflow that removes friction, or a service that records why an action was allowed.

My work sits at the intersection of product thinking, reliable application flows, and documentation that helps another engineer understand the system without guessing. I prefer small, reviewable changes over unexplained rewrites, and I treat validation and release notes as part of the product rather than an afterthought.

## How I work

| Stage | What it means in practice |
| --- | --- |
| **1. Clarify the problem** | Reduce the request to an outcome, a user, and a small useful scope before committing to implementation. |
| **2. Make the flow obvious** | Build interfaces and services that show their state, failures, and next steps clearly. |
| **3. Verify the important paths** | Check behavior, data shape, and setup steps before calling a change complete. |
| **4. Leave a useful trail** | Document the decision, create a release or pull request when appropriate, and make the next contribution easier. |

## Debugging field notes

```text
reproduce the problem
  -> reduce it to the smallest useful case
  -> inspect the data shape and the system boundary
  -> make one understandable change
  -> verify the path that mattered
  -> write down what prevents a repeat
```

The goal is not just to close a bug. It is to leave the codebase more understandable than it was before the bug was found.
